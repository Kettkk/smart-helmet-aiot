One repository, two observable loops

The public workflow separates hardware provenance from reproducible evaluation, then joins both result paths at the backend API.

Telemetry

Simulator or ESP8266 input passes through MQTT, Spring Boot, MySQL, and REST to the Vue dashboard.

input → MQTT → API → MySQL → dashboard

Vision

A SHA-256 verified clip runs through YOLO11n, publishes its benchmark, and appears in the same dashboard.

video → inference → POST → MySQL → dashboard

Evidence kept with the code

Raw measurements, plotting scripts, and publication-ready figures are versioned together.

Physical prototype, explicit boundaries

The public repository preserves the authored device integrations while keeping hardware optional for reproduction.

ESP32-CAM
Camera capture and Wi-Fi image-stream integration.
ESP8266
UART parsing and telemetry bridge to the cloud-facing path.
STM32 boundary
Sensor acquisition originated in an external subsystem; its firmware is not claimed or included.

Physical hardware is not required to reproduce the public telemetry and vision experiments.

Claims stay inside the evidence

The project reports system behavior only. Detection continuity is not precision or recall, and the prototype is not a medical or certified safety device.

Measured
Latency, throughput, continuity, delivery, recovery
Not claimed
mAP, medical validity, energy optimality, field certification
Hardware provenance
ESP32-CAM and ESP8266 firmware; external STM32 source acknowledged

Reproduce the closed loop

Docker Compose starts the broker, database, backend, and dashboard. Simulators keep the evaluation hardware-independent.
